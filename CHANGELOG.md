## v0.4.3 — Оформление кнопок бота

Цвет и иконки на кнопках меню — возможности Bot API 9.4 (февраль 2026).
Миграция `0044`.

### 🎨 Цвет

`style` у кнопки принимает ровно три значения: `primary` (тёмно-синий),
`success` (зелёный), `danger` (красный). Полутонов, осветления и прозрачности
у цветных кнопок в API **нет** — такого поля не существует. Зато отсутствие
поля и есть прозрачная кнопка: клиент рисует её фоном темы.

Отсюда схема «акценты»: цветом выделено одно главное действие, остальные шесть
кнопок прозрачные. Когда покрашены все, акцента не остаётся ни у кого, а меню
выглядит тяжелее, чем прозрачное. Значение настраивается у каждой кнопки и
перекрывает умолчание; `none` гасит цвет явно.

### 🖼 Иконки вместо эмодзи

`icon_custom_emoji_id` показывает кастомную иконку перед текстом.

Если при этом оставить эмодзи в подписи, получится два значка подряд — иконка
и эмодзи. Поэтому при заданной иконке ведущий эмодзи из подписи вырезается
автоматически и возвращается, если иконку убрать. Клавишные эмодзи (`1️⃣`,
`#️⃣`) обрабатываются отдельно: они начинаются с обычного символа и становятся
значком только из-за хвоста `U+FE0F U+20E3`, поэтому цифра режется ровно тогда,
когда этот хвост есть, и никогда — сама по себе.

Иконка задаётся числовым ID кастомного эмодзи, а взять его неоткуда, кроме как
из сообщения: Telegram присылает ID в сущностях того сообщения, где эмодзи
использован. Для этого добавлена команда **`/iconid`** (только админам) —
отправьте боту значки, получите их ID.

### 🛟 Откат, если Premium кончится

Иконки работают только при активном Telegram Premium у владельца бота либо при
купленных на Fragment юзернеймах. Проверить это заранее нельзя: `getMe` такого
не отдаёт.

Premium — подписка, и она истекает. Без защиты каждая отправка меню падала бы
целиком, и человек увидел бы не «меню без иконок», а вообще ничего. Теперь при
отказе Telegram иконки снимаются, сообщение уходит со второй попытки, а факт
запоминается в `telegram_settings.button_icons_ok` — чтобы не упираться в тот же
отказ при каждом нажатии. Повтор безопасен: первая попытка гарантированно ничего
не отправила, Telegram отклонил запрос целиком.

В админке при этом зажигается плашка с кнопкой «Попробовать снова» — иначе после
возобновления Premium флаг остался бы `false` навсегда и иконки не вернулись бы.

### 🧹 Попутно

Исправлена устаревшая подсказка в админке: там говорилось, что действие кнопки
определяется по эмодзи в подписи, хотя оно берётся из поля `action`. С иконками
эмодзи из подписи убирается — подсказка сбивала бы с толку ровно в новом
сценарии. Заодно в редакторе кнопок появились переключатель «широкая» и выбор
цвета, которых там не было.

## v0.4.2 — Логи стали читаемыми

Патч к v0.4.1. Логи появились, но оказались втрое избыточнее нужного, а деплой
не применял к nginx настройки из compose.

### 🔇 Один запрос — одна строка

Каждый запрос писался трижды: edge-nginx, backend и nginx внутри контейнера
frontend. Плюс User-Agent на 120 символов в каждой строке и чекпоинт Postgres
раз в несколько минут круглосуточно. Одна загрузка страницы админки давала под
три десятка строк, и полезные записи тонули среди статики и опросов.

Роли разведены — каждое событие пишет кто-то один:

| Источник | Что пишет |
|---|---|
| backend | каждый запрос к API — с номером пользователя и назначением |
| nginx (edge) | только 4xx/5xx и ответы дольше 2 с |
| nginx внутри frontend | ничего: он за edge-nginx, всё было бы третьей копией |
| Postgres | ошибки; запись каждого чекпоинта отключена |

Строка backend содержательнее прочих: там есть номер пользователя и назначение
(«оплата», «админка»), которых у nginx нет в принципе. Поэтому дублирующие
записи убраны именно у nginx, а не наоборот.

Порог «медленно» у nginx берётся регэкспом по `$request_time` — проверено на
девяти значениях, срабатывает ровно от 2.000 с. User-Agent подставляется только
к 4xx/5xx, где он и нужен: для разбора ошибки и опознания сканера. Переменные
внутри значения `map` nginx раскрывает — это тоже проверено отдельно.

У Postgres отключена запись чекпоинтов: с 15-й версии она включена по умолчанию
и даёт строку на 250 символов про буферы и WAL, бесполезную при разборе аварии.

В «молчаливые» у backend добавлены опросы, которые фронт дёргает на каждой
навигации: `/api/maintenance/status` и `/api/admin/public/config`. Ошибки и
медленные ответы по этим путям пишутся по-прежнему.

Размен осознанный: успешные загрузки страниц и статики не видны нигде. Для
счётчиков посещаемости лог контейнера всё равно не годится, а объём они давали
основной. Как вернуть полную запись на время разбора — в `DEPLOY.md`.

### 🔁 Деплой не применял настройки к nginx

`deploy.sh` делал nginx `restart`, а он поднимает тот же контейнер с прежним
`HostConfig` — то есть изменения в `docker-compose.yml` для nginx не применялись
никогда. Вскрылось на ротации логов из v0.4.1: лимит прописали всем семи
сервисам, деплой прошёл, а nginx — единственный, кто пишет строку на каждый
запрос, — остался со старым конфигом и накопил 104 МБ.

Теперь `up -d --force-recreate`: применяет настройки и так же обновляет upstream
IP, ради чего рестарт там и стоял. Простой тот же.

Заодно в конце деплоя сверяются все контейнеры проекта: у кого пустой
`LogConfig.max-size`, тот пишет лог без предела, пока не кончится диск. Снаружи
это незаметно — теперь выводится предупреждение с готовой командой. Имя сервиса
берётся из метки `com.docker.compose.service`: имя контейнера имеет вид
`<проект>-<сервис>-<номер>`, и обрезка префикса оставляла хвост «-1», с которым
подсказанная команда не работала.

## v0.4.1 — Логи, выдача доступа и обучение ассистента

Три подсистемы, которых не было вовсе: человеческие логи, повторная выдача
доступа после оплаты и база знаний ИИ-ассистента. Плюс просмотр переписки в
тикетах и предупреждение о втором аккаунте в боте. Миграции `0041`–`0043`.

### 📋 Логи

Логов как таковых не было: 470 голых `console.*` без времени и уровня, ни одной
записи о HTTP-запросах и никакой ротации.

`services/logger.js` даёт единый формат — время в местной зоне, уровень, раздел.
Технические ошибки переводятся на человеческий: `relation "…" does not exist`
превращается в «нет такой таблицы — скорее всего не применена миграция»,
`ECONNREFUSED` — в «служба не запущена или закрыт порт». Технический текст при
этом остаётся в скобках, по нему ищут в поиске.

Существующие 470 вызовов подхватились сами: `logger.install()` оборачивает
консоль одной строкой. Переписывать 470 мест значило бы 470 шансов что-нибудь
задеть.

`middleware/requestLog.js` — строка на каждый запрос. Раньше разобрать «кто,
когда и чем дёрнул» было не по чему.

**Секреты в лог не попадают.** Это была главная забота: через query-строку у нас
ездят одноразовые токены входа (`/auth/tg-login?t=…`) и сброса пароля. Тело
запроса не пишется вообще, от параметров остаётся пометка `(+параметры)`,
значения маскируются по ключу и по виду — JWT, OAuth Яндекса, токены ботов,
hex-ключи, `Bearer`.

nginx переведён на тот же формат, и там была та же дыра: `$request` содержит
строку запроса целиком, то есть токены писались в открытую. Теперь `$uri` и
пометка. Кириллица потребовала `escape=json`: при умолчании nginx экранирует все
байты старше 0x7F, и русский текст превращается в `\xD0\xB7…`. Защита от
подделки записей при этом сохраняется — `%0A` попадает в лог как `\n`.

**Ротация.** Её не было нигде: драйвер `json-file` писал без предела, пока не
кончится диск. 20 МБ × 5 на сервис в `docker-compose.yml`, плюс `install.sh`
кладёт общий предел в `/etc/docker/daemon.json`.

### 🔑 Оплачено ≠ выдано

`activateSubscription` писала подписку в базу независимо от того, создался ли
пользователь в RemnaWave. Панель не ответила или у тарифа пустой `squad_uuids` —
в базе появлялась строка с `is_active = true` и `remnwave_user_uuid = NULL`:
человек заплатил, видит активную подписку и не может подключиться. Ошибка никуда
не всплывала: активация не падала, вебхук отвечал 200, в логе значилось
«Created new subscription … with new Remnwave user».

Появилось состояние выдачи (`ok` / `pending` / `failed`), `services/provisioning.js`
с повторами и крон раз в минуту: 10 попыток за ~11 часов, с нарастающей паузой.
Строка забирается атомарно через `FOR UPDATE SKIP LOCKED` — два тика не станут
править одного пользователя в панели разом. Срок подписки при повторе берётся из
базы, а не считается заново: иначе человек терял бы дни, пока мы чинимся.

`is_active` при этом НЕ снимается. Снять — значит показать заплатившему «подписки
нет»; он решит, что деньги пропали, и вдобавок сможет взять пробник поверх
оплаченного тарифа. Подписка оплачена и существует — не выдан только доступ, и
это разные вещи.

Уведомления `admin_provisioning_failed` и парное `admin_provisioning_fixed`.
Отдельно `admin_activation_failed` — на случай, когда активация падает целиком и
подписки нет вовсе: у `payments.plan_id` внешний ключ `ON DELETE SET NULL`, так
что удалённый во время оплаты тариф обнуляет ссылку, и чинить кроном нечего.

Тариф без серверной группы больше не сохранить активным: раньше каждая покупка
такого тарифа давала мёртвую подписку.

В кабинете — плашка «Готовим доступ». Без неё человек видит активную подписку,
к которой невозможно подключиться, и делает единственный доступный вывод.

Миграция `0041` заодно лечит прошлое: существующие активные подписки без
`remnwave_user_uuid` ставятся в очередь на повтор.

### 🎓 Ассистент учится

Ассистент не учился вообще: промпт собирался из статичного текста и шаблонов,
написанных руками, — их в базе был один. Журнал копил его собственные ответы, но
обратно в промпт они не попадали никогда.

Дообучения модели тут нет и быть не может — веса не наши. Работает иначе: храним
пары «вопрос клиента → ответ живого оператора» и перед каждым тикетом
подкладываем несколько самых близких. Снаружи разницы нет, а плюсов больше —
действует сразу, откатывается выключением строки, и видно, на чём построен ответ.

Поиск — встроенный полнотекстовый Postgres с русской морфологией, без внешних
вызовов и эмбеддингов. Связка слов через ИЛИ, а не И: `plainto_tsquery` требует
в примере все слова вопроса сразу, и на живом обращении в три строки это не
срабатывает — проверено, ноль совпадений на 17 примерах.

Примеры уходят в пользовательское сообщение, а не в системный промпт: системный
помечен `cache_control` и одинаков для всех тикетов, подмешав туда примеры мы
обнуляли бы кэш на каждом вызове.

**Ответы самого ассистента в базу не идут** — учиться на себе значит закрепить
собственную ошибку. Отличаем по тексту: в API бота оператор и ассистент помечены
одинаково. **Правка оператора поверх ответа ассистента** весит втрое больше
рядового примера: это прямое указание, где он ошибся, а человек знал как надо.

С боевых тикетов собрано 68 пар из 83 тикетов. Не прошедшие отбор не
выбрасываются, а сохраняются выключенными и с причиной (`0043`): решение «этому
учиться не стоит» принимал регэксп, и молча — теперь это видно и включается
одним нажатием. Отбор отсеивает дежурные закрытия по давности и переводы в личку:
выучив их, ассистент начал бы отвечать «закрываем обращение» и раздавать чужой
личный контакт.

Вкладка **База знаний** в `/admin/ai`: счётчики, список, проверка «что
подберётся под такой вопрос».

### 💬 Переписка в тикетах

Данные были доступны, эндпоинт написан, а посмотреть диалог глазами было нельзя —
таблица показывала только тему и статус.

Клик по тикету открывает переписку как чат. Реплики ассистента помечены отдельно:
в API бота он и оператор приходят одинаково, и без пометки не понять, кто на
самом деле отвечал клиенту. Под ответом оператора — его судьба в базе знаний и
кнопка добавить или включить.

### 👤 Второй аккаунт в боте

Бот ищет человека по `telegram_id`, сайт — по `telegram_oidc_sub` или по почте.
Это разные идентификаторы, поэтому `/start` без привязки заводит второй аккаунт,
и подписка, купленная на сайте, в боте не видна.

Проверка двойника при `/start` — зеркало той, что уже была в OIDC-колбэке. Сливать
по `@username` по-прежнему нельзя: ник меняют, освободившийся достаётся другому,
и автослияние стало бы захватом чужого аккаунта с подпиской. Поэтому только
предупреждение: админу в лог, человеку — сообщением со ссылкой на привязку.

Кнопка ведёт в браузер, а не в Mini App: Mini App открылся бы от лица этого чата,
то есть от нового пустого аккаунта, а привязывать нужно из старого кабинета.
Разделы кабинета теперь открываются ссылкой — `/dashboard?section=security`.

## v0.4.0 — Отдача рассылок и мобильная вёрстка

ИИ-планировщик рассылок научился считать деньги и не повторяться, а на
телефоне перестали проваливаться тапы по меню. Минорный номер: миграция схемы,
три новых эндпоинта и новые данные в промпте модели.

### 💰 Атрибуция выручки

Модель видела «блокировок в сутки», но не видела главного — принесла рассылка
денег или нет. Теперь считается выручка за сутки после отправки относительно
обычного дня.

База — **тот же день недели за три предыдущие недели**, а не «вчера»: выручка
сильно зависит от дня, и сравнение с соседним днём давало бы шум вместо
сигнала. Рассылки с базой меньше 500 ₽ в расчёт не идут — при базе в 60 ₽ одна
случайная покупка рисует «рост в тридцать раз», и такие числа затопили бы
статистику.

На живых данных посчиталось по 94 рассылкам из 111. Медиана по всем — **x0.94**,
то есть рассылки в среднем себя не окупают. Единственный сегмент с реальной
отдачей — `expired` (**x1.29** по 12 рассылкам), которому при этом не писали
51 день.

В промпт отдача попадает отдельной припиской, а не как «ПРАВИЛО», и только при
пяти и более рассылках: по трём медиана скачет от одной удачной отправки, и
модель выучила бы шум. В интерфейсе — блок «Отдача в деньгах» на вкладке
настроек, грузится лениво: перебор всех пополнений бота это тысячи записей.

### 🔁 Защита от повторов

Похожесть текстов по коэффициенту Жаккара на множествах слов. Сравнение по
началу строки ловит только буквальные копии — достаточно поменять первое
предложение, и повтор пройдёт; по набору слов совпадение видно даже при
переставленных абзацах.

Проверка **учитывает сегмент**, и это принципиально. В истории 34 почти
одинаковых сообщения за две недели, но 13 из них — одно сообщение разным
аудиториям, и это нормальная практика: сказать одно и то же тем, кто без
подписки, и тем, у кого она истекла. Настоящая проблема — оставшийся 21
повтор в ТОТ ЖЕ сегмент, иногда через 18 часов. Проверка без учёта сегмента
ругалась бы на законные рассылки и быстро научила бы их игнорировать.

Для ИИ повтор — жёсткий запрет: отправка не уходит. Человеку то же самое
показывается предупреждением на шаге подтверждения, кнопка остаётся активной —
причина отправить повтор бывает, и знает её человек, а не модель. Порог и окно
настраиваются (по умолчанию 0.70 и 14 дней, значение 1.0 выключает проверку).

Модель дополнительно получает в промпт восемь последних текстов под заголовком
«НЕ ПОВТОРЯЙ».

### 🧪 Полигон

Флаг `is_sandbox` у сегмента: здесь разрешено пробовать непривычные
формулировки, не рискуя всей базой. Помечен `expiring` — 34 человека против
5418 у `all`, при этом за восемь месяцев ему написали трижды.

Заодно даты в промпте заменены на дни простоя: «не писали 51 дн.» вместо
«последняя 2026-07-21» — дату модели пришлось бы вычитать из сегодняшней в
уме. В правилах сегментов простой от 30 дней подсвечивается.

Миграция `0040`.

### 🐛 Настройки ИИ молча не сохранялись

`updateSettings` отбрасывал все поля, которых нет в списке `FIELDS`, а список
не расширили после миграции `0037`. Роут при этом отвечал 200, и интерфейс
показывал «Сохранено» — худший вид ошибки.

`FIELDS` стал картой «поле → тип»: приведение по умолчанию делало `Number(v)`,

сразу, а не через неделю.

### 📱 Мобильная вёрстка: тапы по меню не доходили

Причина у всех трёх случаев одна — `position: fixed`, запертый в чужом
контексте наложения.

**Меню шапки жило внутри самой шапки.** У шапки `backdrop-blur`, а он делает её
containing block для `fixed` (те же грабли, что у панели уведомлений).
Затемнение `inset-0` получало высоту шапки, а не экрана — 7px вместо 720, и тап
мимо меню его не закрывал. Отступ сверху был жёстко вписан как 65px, тогда как
шапка 73px, а с домашнего экрана iPhone — 132px: **меню наезжало на шапку на
67px**, логотип скрывался, а под кнопкой бургера оказывался пункт меню, и тап
«закрыть» уводил на другую страницу. Меню вынесено порталом в `body`, отступ
берётся из реальной высоты шапки с пересчётом при повороте экрана. Заодно меню
закрывается при смене страницы: ссылки закрывали его сами, но переход бывает и
мимо них.

**Модальные окна кабинета оказывались под нижней панелью.** Обёртка `.dp > *`
имела `z-index: 1` и становилась контекстом наложения — всё внутри упиралось в
этот потолок, хотя окна объявляют `z-50`. Панель разделов, соседний элемент с
`z-40`, рисовалась выше: тап по кнопке внизу модалки попадал в панель и
переключал раздел вместо оплаты. `z-index` снят — порядок отрисовки сохраняется
сам, декоративный слой идёт в разметке раньше содержимого.

**Вкладки, обрезанные по правому краю.** Корневая обёртка админки —
`overflow-x: hidden`, поэтому всё, что не влезло, пропадает без полосы
прокрутки. «Шаблоны» и «ИИ» на странице рассылок (четыре вкладки занимают 478px
при экране 393), кнопка «Создать» в промокодах, вкладка «Пользователи» в
серверах. Первым дана прокрутка вбок — ужать отступы мало, счётчики в подписях
растут; остальные переносятся и ужимаются.

Проверено эмуляцией iPhone 15 Pro с подставленными отступами безопасной зоны:
попадание тапов измерялось через `elementFromPoint`, а не на глаз. Все 38
страниц админки прогнаны на обрезанные элементы управления.

## v0.3.0 — Промокоды и рассылки

Две новые подсистемы и три исправления в платежах. Минорный номер: шесть
миграций схемы, новый крон и новый внешний поток (рассылки через API бота).

### 🎟 Промокоды

Свои коды проекта — не путать с `/admin/bedolaga/promo`, где чужие коды
стороннего бота (тот пункт переименован в «Промокоды бота»).

Четыре типа: процент, фиксированная сумма, дни подписки, деньги на баланс.
Ограничения: общий лимит и лимит на пользователя, окно действия, минимальная
сумма заказа, привязка к тарифам и периодам, «только первая покупка», возраст
аккаунта, персональные коды для компенсаций.

**Резерв вместо мгновенного списания.** Оплата через шлюз живёт до 30 минут и
может не состояться: считать код потраченным сразу — брошенная оплата сожжёт
активацию, считать только при подтверждении — пользователь откроет пять вкладок
с одноразовым кодом и оплатит все пять. Отсюда состояния
`reserved → applied | released`.

Четыре правила, на которых всё держится:

1. **Корректность не зависит от крона.** Резерв с истёкшим сроком не
   учитывается в лимите самим запросом — код освобождается по времени.
2. **`reserved_until` = час**, а не `payments.expires_at`: на момент резерва
   его ещё нет, он записывается после ответа платёжки.
3. **`confirm()` лимит НЕ проверяет.** Платёж в статусе `expired` может стать
   `completed` (см. v0.2.1) — подтверждение по СБП приходит и через час, когда
   резерв уже отдан другому. Отказать в скидке тому, кто заплатил, хуже, чем
   выпустить активацию сверх лимита: ставится флаг `over_limit`.
4. **Скидка считается один раз и сохраняется** — правка кода между оплатой и
   вебхуком не меняет согласованную сумму.

Скидка применяется при покупке подписки, оплате с баланса и смене тарифа. При
смене считается от ДОПЛАТЫ, а не от цены тарифа. Проверка кода и резерв —
внутри транзакции под `FOR UPDATE`: в роуте осталась только предварительная
проверка для выбора ветки.

Активация кодов на дни и баланс — в кабинете и командой `/promo` в боте.
Бот **не создаёт аккаунт**: вход через бота ищет по `telegram_id`, через
браузер по `telegram_oidc_sub`, и `findOrCreateUser` завёл бы человеку второй
аккаунт мимо его настоящего кабинета.

Защита от перебора: свой лимитер, считающий **неудачные** попытки.
`skipSuccessfulRequests` считает успехом любой статус ниже 400, поэтому отказ
отдаётся кодом 400 — иначе перебор не штрафовался бы вовсе.

Админка: список со счётчиками, форма с расшифровкой условий человеческим
языком, генератор пачек (алфавит без `0/O` и `1/I/L` — коды диктуют голосом),
журнал активаций, выгрузка CSV. Миграция `0034`.

### 📣 Рассылки Bedolaga

Отдельная страница `/admin/bedolaga/broadcasts`.

**Белый список сегментов был неверен.** Разрешалось пять значений, но сегмент
`no` (второй по частоте — 38 из 110 рассылок) в нём отсутствовал: отправить

**Размер аудитории показывается до отправки.** Главная цифра — сколько бот
реально взял в прошлый раз. Собственная оценка по базе сверяется с этим фактом
и показывается только при расхождении до 10 %: проверка выявила, что из шести
сегментов совпадает один. По `trial` расхождение было **в 55 раз** (56 против

рассчитывая на полсотни человек.

**Метрика блокировок считается корректно.** `blocked_count` у бота относится к
сегменту, а не ко всей базе: разность между соседними записями общего списка
даёт «−475 заблокировавших». Сравниваются только соседние рассылки одного
сегмента, и прирост делится на дни — иначе он растёт просто от длины интервала.

Подтверждение отправки в три шага, для сегментов от 1000 человек — с вводом
числа получателей вручную. Отменить рассылку у API бота нельзя.

Настройки: минимальный интервал, недельный лимит, тихие часы (окно может
переходить через полночь), порог подтверждения, разрешённые сегменты.
Шаблоны текстов. Свой журнал отправок — лимиты считаются по тому, что
отправили мы, а не по истории бота. Миграция `0036`.

### 🤖 ИИ-планировщик рассылок

Три режима: выключен, **подготовка** (готовит карточку, отправляет человек),
**автопилот** (отправляет сам).

Учится на 110 прошлых рассылках: лучшие по приёму идут образцами, худшие —
антипримерами, отклонённые предложения с причинами — чтобы не предлагать одно
и то же по кругу. Разброс сигнала реальный: у лучших 0 блокировок в сутки, у
худших 134–158.

**Автопилот с окном отмены.** Раз у API нет отмены, страховка ставится до
вызова: рассылка встаёт в очередь, админу уходит уведомление в Telegram, и
через заданное время (по умолчанию 30 мин) диспетчер отправляет. Диспетчер
забирает задачу атомарным `UPDATE ... WHERE status='scheduled'` — два
параллельных тика не отправят дубль, которого API бота не отличит.

Лимиты перепроверяются **в момент отправки**: за время окна владелец мог
поменять настройки. Не прошло — рассылка возвращается человеку с причиной, а
не теряется молча. Аварийный выключатель гасит автопилот и снимает очередь.

**Правила по сегментам** (миграция `0039`): разрешение для ИИ и для человека
по отдельности, назначение (любые / продающие / сервисные), свой интервал и
пояснение, попадающее в промпт. Проверяются кодом, а не уговорами в промпте.

Кодом же проверяется главное: лимиты до обращения к модели, порог уверенности,
допустимость сегмента и **промокоды, которых нет среди активных** — модель
может выдумать «SALE30», и запрет в промпте обходится, а проверка нет.

Миграции `0037`, `0038`.

## v0.2.3 — Тема после сворачивания, вход сразу в кабинет, панель разделов

### 🐞 Тема «залипала» после возврата из фона

Тема применялась один раз — при монтировании и при смене настройки, — а
дальше её отслеживал единственный слушатель `change` у `matchMedia`. iOS
усыпляет JS свёрнутого приложения, и события, случившиеся в это время, до
страницы не доходят вообще: они не откладываются, а теряются. После
сворачивания и возврата состояние расходилось с системным и висело так до
полного перезапуска — при холодном старте значение читается заново.

Обработчиков `visibilitychange` и `pageshow` в проекте не было ни одного.
Теперь тема пересчитывается на каждом возврате приложения на передний план.
`pageshow` нужен отдельно: возврат страницы из bfcache не всегда меняет
`visibilityState`.

### 🐞 Два источника цвета окна расходились

Система читает цвет из двух независимых мест, и они противоречили друг другу:
`<meta name="theme-color">` в `index.html` был светлый (`#f0f9ff`), а
`theme_color` в `manifest.json` — тёмный (`#060913`). Пока жив JS, работает
мета-тег; когда окно перерисовывает система — берётся манифест. Оба сведены к
тёмному, под цвет экрана запуска; инлайн-скрипт успевает перекрасить в светлый
до первой отрисовки.

### 🐞 Класс тёмной темы утекал из premium-кабинета

`DashboardUiContext` добавлял `dark` на `<html>` и никогда его не снимал — в
cleanup убирался только `dp-theme`. Уйдя из premium-кабинета, пользователь со
светлой темой оставался в тёмной до перезагрузки страницы.

Заодно `AdminLayout`, `AdminLayoutV2` и `DashboardUiContext` держали каждый
свою копию восстановления темы через `localStorage` + `matchMedia`, и копии
уже разъехались. Теперь общий `lockDarkTheme()`: раздел ставит
`data-theme-lock="dark"` на `<html>`, пересчёт при возврате из фона это
уважает и не сбрасывает админку в светлую, а `theme-color` красится вместе с
классом (раньше в админке со светлой темой страница была тёмной, а полоска
статус-бара — светлой).

### 🚀 Запуск приложения открывает кабинет

Ярлык с домашнего экрана открывает `start_url`, то есть `/` — авторизованному
там показывать нечего. Новый `HomeRoute` уводит его на `/dashboard`. Ссылка
«Главная» в шапке для авторизованных ведёт на `/?home`, иначе пункт меню был
бы нерабочим; этот же адрес позволяет посмотреть лендинг, не выходя из
аккаунта.

### 📱 Нижняя панель разделов в теме Digital Premium

Была `position: sticky` — полоса прилипала к низу своего контейнера и уезжала
вместе с прокруткой, а шесть разделов внутри приходилось листать вбок
(`overflow-x`).

- `position: fixed` — панель прибита к экрану. `.dp` имеет только
  `position: relative`, без `transform` и `backdrop-filter`, поэтому
  containing block не создаёт.
- Пункты разложены сеткой в равные колонки (`grid-auto-flow: column`): видно

- Иконка сверху, подпись снизу — как в обычной теме. Для колонки ~59 px

  целиком не помещались.
- Отступ под home-индикатор iPhone и под «уши» в альбомной ориентации.
  Место под панель — отступом на `body`, иначе подвал сайта (он рендерится
  вне `.dp`) оказывался бы под полосой.
- Счётчик непрочитанных — кружком на углу иконки; переключение раздела
  прокручивает страницу вверх.

## v0.2.1 — Пополнение баланса не зачислялось

Разбор реального случая: пополнение на 100 ₽ прошло у Platega (`CONFIRMED`),
но на баланс не попало. Нашлись три независимых причины — каждой хватило бы
в одиночку.

### 🐞 `expired` ломал зачисление навсегда

`expires_at` платежа — это время жизни платёжной **формы**, которое вернула
Platega (30 минут). Крон `expireOldPayments` по нему переводит платёж
`pending` → `expired`. Но в таблице переходов `ALLOWED_STATUS_TRANSITIONS`
статуса `expired` не было: поиск давал `undefined`, код подставлял пустой
`Set`, и **любой** колбэк отвергался как недопустимый переход — с ответом
`200 OK`, так что провайдер считал доставку успешной и не повторял.

Истечение формы не означает «денег не будет»: подтверждение по СБП вполне
приходит позже. Теперь `expired` — полноправный исходный статус, из него
платёж может стать `completed`, `failed` или `refunded`.

Начисление на кошелёк срабатывало строго на `pending → completed`. Если бы
поправили только таблицу переходов, платёж из `expired` стал бы `completed`
**без зачисления денег** — то есть незаметно. Оба места теперь используют
общий список `UNPAID_STATUSES`.

### 🐞 Комиссия сверх суммы отбивала колбэк

При `comissionType: 0` Platega добавляет комиссию к сумме и списывает её с
плательщика: счёт на 100 ₽ проводится как 108 ₽. Проверка требовала точного
совпадения и вернула бы `400` на подтверждённый платёж.

Теперь проверяется **недоплата**, а не равенство. Переплата безопасна — на
баланс идёт `payment.amount`, а не сумма из колбэка; опасна недоплата, её и
отсекаем с допуском в копейку.

### 🐞 Статус чарджбэка

Ждали `CHARGEBACK`, документация Platega описывает `CHARGEBACKED`. Возврат
уезжал в `default` → `pending`, и деньги оставались на балансе после
чарджбэка. Принимаются оба написания.

### 🛠️ Сверка платежей

`backend/scripts/reconcile-payments.js` — спрашивает у Platega реальный статус
незакрытых платежей и добивает подтверждённые:

```bash
docker compose exec backend node scripts/reconcile-payments.js            # разбор
docker compose exec backend node scripts/reconcile-payments.js --apply    # зачислить
docker compose exec backend node scripts/reconcile-payments.js --id 14 --apply
```

Запрос статуса — GET, повторять безопасно. Изменения применяются той же
функцией, что обрабатывает вебхук (`processPlategaWebhook`): транзакция,
`SELECT ... FOR UPDATE`, машина состояний, идемпотентность. Повторный запуск
не задваивает. По умолчанию — разбор без изменений.

### ⚠️ Проверьте настройки Platega

Адрес колбэка **не передаётся** в запросе создания транзакции — схема
`CreateTransactionRequest` такого поля не содержит. Он задаётся в кабинете
мерчанта: Настройки → Callback URLs → `https://ваш-домен/api/payments/webhook`.
Если там пусто, вебхук не придёт никогда и баланс не пополнится.

Там же стоит проверить адрес возврата: если `FRONTEND_URL` не задан, в Platega
уходит `http://localhost:5173`, она его отбрасывает (в транзакции
`"return": null`), и плательщик остаётся на странице провайдера вместо сайта.

## v0.1.34 — Два кабинета у одного Telegram-аккаунта

### 🔀 Причина расхождения

Вход через бота (и Mini App) ищет пользователя по `telegram_id`, а вход через браузер («Войти через Telegram», OIDC) — по `telegram_oidc_sub`, оставляя `telegram_id` пустым. Идентификаторы **разные** — Telegram OIDC не возвращает `telegram_id`. Из-за этого один человек получал **два независимых аккаунта**: подписка, активированная в боте, не отображалась в кабинете, открытом из браузера, и наоборот.

### 🛠️ Слияние существующих дублей

Добавлен административный скрипт `backend/scripts/merge-telegram-duplicates.js`:

```bash
docker compose exec backend node scripts/merge-telegram-duplicates.js          # разбор без изменений
docker compose exec backend node scripts/merge-telegram-duplicates.js --apply  # выполнить слияние
```

- Находит пары по совпадению `@username` и показывает, какие данные у каждого аккаунта, **не меняя ничего** без флага `--apply`.
- Переносит на основной аккаунт (тот, у которого есть `telegram_id`) подписки, платежи, уведомления и остальные связи; балансы кошельков складываются.
- Копирует туда же `telegram_oidc_sub` — после слияния **оба способа входа ведут в один кабинет**.
- Работает в транзакции: при любой ошибке изменения откатываются целиком.

### ⚠️ Про новые дубли

Связывать аккаунты по `@username` автоматически при входе **нельзя** — username в Telegram можно сменить и переуступить, это открыло бы захват чужого аккаунта. Поэтому при создании второго аккаунта backend теперь пишет явное предупреждение в лог с подсказкой, как выполнить слияние.

## v0.1.31 — Исправлен вход через Telegram на сайте

### 🔐 Вход по ссылке из бота больше не срывается

Причина, найденная по логам сервера: фронтенд обменивал одноразовый токен **дважды** — первый запрос успешно выдавал JWT, второй получал `410 used` и показывал ошибку поверх уже состоявшегося входа.

- **`/tg-login`** дополнительно защищён от повторного обмена через `sessionStorage` — переживает перемонтирование. Если токен уже обменян и вход состоялся, страница просто продолжает переход, а не показывает ошибку.

## v0.1.30 — Вход через Telegram: точная причина отказа

### 🔐 Вход по ссылке из бота (`/auth/tg-login`)

- **Одноразовый токен больше не сгорает до проверки прав.** Раньше он помечался использованным сразу, поэтому после любого отказа повторный переход давал «токен невалиден или истёк» и маскировал настоящую причину. Теперь: проверка токена → проверка прав → и только затем токен считается израсходованным.
- **Понятная причина отказа** вместо одной общей формулировки: ссылка не найдена / уже использована / истёк срок (5 минут) / повреждена. Причина возвращается пользователю и пишется в лог backend (`[tg-login] отказ: <reason>` с `used_at`, `expires_at`, `user_id`, `ip`) — по нему видно, что именно произошло на сервере.

### 🐛 Фиксы

- **После входа приходилось обновлять страницу.** `MaintenanceGate` проверял статус только при монтировании, поэтому до 30 секунд (или до F5) продолжал считать вошедшего гостем — в админском режиме это показывало «Доступ ограничен» уже авторизованному админу. Теперь статус перепроверяется при переходе между страницами и при появлении/пропаже токена.

## v0.1.22 — Hotfix: rate-limit съедал info/poll-endpoints → 429 везде

После v0.1.19 на `/auth/*` стоял глобальный `authLimiter` — 20 запросов / 15 минут на IP. Это рушит сразу несколько фич, добавленных в v0.1.19:

- `/auth/register/poll` поллится **раз в 2 сек** до 15 мин — это до 450 запросов на одного юзера в форме регистрации через бот.
- `/auth/telegram/link/poll` — то же самое для привязки.
- `/auth/telegram/availability`, `/auth/telegram/oidc/info` пингуются **на каждой загрузке** `/login` и `/register`.

Юзер выжирает лимит мгновенно, дальше — 429 на всё:
- кнопка «Войти через Telegram» (OIDC) пропадает с `/login`
- кнопка «Регистрация через бот» пропадает с `/register`
- классический `/auth/login` отвечает «Too many auth attempts»

**Фикс:**

1. **Backend** — в [`backend/index.js`](backend/index.js) `authLimiter.skip()` теперь пропускает все idempotent / polling / one-time-token endpoints. Жёсткий лимит остаётся только на brute-force-уязвимые: `/login`, `/register`, `/send-code`, `/forgot-password`, `/reset-password`, `/confirm-email`, `/register/start`, `/telegram/link/start`.

   Skip-список:
   ```
   /telegram/availability   /telegram/oidc/info
   /telegram/oidc/start     /telegram/callback
   /register/poll           /telegram/link/poll
   /tg-login
   ```
   Все они защищены либо непредсказуемым one-time токеном (атомарный `used_at`), либо state+PKCE+client_secret (OIDC).

2. **Frontend** — кнопки теперь кэшируют последний успешный ответ от `/availability` и `/oidc/info` в `sessionStorage`. Если следующий запрос провалится (429/network/CORS) — фронт переиспользует кэш и кнопка не исчезает.

После деплоя контейнер backend стартует с чистым in-memory rate-limit store — **все накопленные счётчики сбросятся**, юзеры смогут войти сразу.

## v0.1.20 — Hotfix: OIDC sub != telegram_id (BIGINT overflow)

При входе через OIDC падало с `value "11713064933933089000" is out of range for type bigint`. Причина: OAuth/OIDC `sub` claim — это **opaque subject identifier**, а не реальный telegram_id (который приходит через `ctx.from.id` в боте). Telegram возвращает sub значениями ~1.17×10¹⁹, что больше PostgreSQL `BIGINT` (макс 9.2×10¹⁸).

**Фикс:**

- Миграция [`0014_users_oidc_sub`](backend/migrations/0014_users_oidc_sub.up.sql) — отдельная колонка `users.telegram_oidc_sub VARCHAR(64)` + UNIQUE INDEX (partial, WHERE NOT NULL).
- В [OIDC callback](backend/routes/auth.js) теперь:
  - sub читается как строка (не парсится в int)
  - find/create юзера идёт **по `telegram_oidc_sub`**, не по `telegram_id`
  - `telegram_id` оставляется NULL — он будет проставлен **только когда юзер сделает `/start` в боте** через привязку из `/dashboard → Безопасность`.

**Trade-off:** юзер, зашедший через OIDC, получает аккаунт, но бот ему писать не сможет (нужен реальный chat_id). Чтобы получать TG-уведомления — пусть откроет «Привязать через Telegram-бот» в `/dashboard → Безопасность` (мы добавили эту кнопку в v0.1.19) — handler `/start link_<token>` корректно проставит реальный `telegram_id`.

## v0.1.17 — Telegram OAuth 2.0 / OpenID Connect

Добавлен полноценный OIDC-вход параллельно с Login Widget. В отличие от виджета (HMAC поверх данных через `bot_token`), это стандартный flow `authorization_code + PKCE` через [oauth.telegram.org](https://oauth.telegram.org/.well-known/openid-configuration). Креды (`client_id` + `client_secret`) выдаёт `@BotFather` отдельно от `bot_token` командой `/newoauth`.

**Что нового:**

- Миграция `0012_telegram_oidc` — поля `oidc_enabled`, `oidc_client_id`, `oidc_client_secret` (encrypted), `oidc_redirect_uri` в `telegram_settings`.
- `backend/services/telegramBot/oidc.js` — клиент OIDC: `genState`, `genPkce`, `buildAuthUrl`, `exchangeCode`, `verifyIdToken` (через JWKS, RS256, кэш 10 мин).
- `GET /auth/telegram/oidc/start` — генерит state + PKCE (S256), кладёт в подписанную httpOnly-cookie на 5 мин, редиректит на `https://oauth.telegram.org/auth?...`.
- `GET /auth/telegram/callback` — сверяет state, обменивает code на токены, валидирует ID Token (JWKS RS256, iss, aud, exp), мапит `sub → telegram_id`, выдаёт одноразовый auto-login токен и редиректит на `/tg-login?t=...` (фронт уже умеет такое).
- `GET /auth/telegram/oidc/info` — публичный, отвечает `{ available: true|false }`. Фронт `/login` его пингует чтобы решить, показывать ли OIDC-кнопку.
- UI: новая карточка «OAuth 2.0 / OpenID Connect» в `/admin/telegram → Подключение` с полями Client ID / Client Secret / Redirect URI и галочкой включения.
- UI: на `/login` отдельная кнопка «Войти через Telegram (OIDC)» — показывается только когда настройки полные и галочка включена.

**Что нужно сделать у @BotFather** (одноразово):

1. `/newoauth` → выбрать бота → BotFather пришлёт `Client ID` + `Client Secret`.
2. `/setoauthredirects` → бот → ввести redirect URI (`https://your-domain/auth/telegram/callback`).

**Что нужно в админке** `/admin/telegram → Подключение → OAuth 2.0 / OpenID Connect`:

1. Вставить `Client ID`, `Client Secret`, `Redirect URI`.
2. Включить галочку «Включить OIDC-вход».
3. Сохранить.

Login Widget продолжает работать как и раньше — это две независимые точки входа.

## v0.1.16 — TG Login Widget: TTL 24ч, диагностика, аватар в кнопке

Прошёлся по [официальной docs](https://core.telegram.org/widgets/login) Telegram Login Widget. HMAC-проверка у нас уже корректная (sort → key=value → \n → SHA256(token) → HMAC_SHA256), но три улучшения:

**1. `auth_date` TTL: 5 минут → 24 часа**
В docs Telegram не указывает максимум. Прежние 5 минут — наша инициатива, на медленном интернете юзер мог не успеть нажать виджет → подтвердить → вернуться на сайт. 24 часа — стандарт защиты от replay-атак при перехвате.

**2. Диагностика причины 401**
`verifyTelegramData()` теперь возвращает `{ ok, reason }`. Backend на 401 шлёт человекочитаемый `hint`:
- `no_bot_token` → «Открой /admin/telegram → Подключение и сохрани токен»
- `hash_mismatch` → «Token не совпадает с BotFather, или /setdomain не сделан»
- `auth_date_expired` → «Сессия 24+ часов, перезагрузи страницу»
- `auth_date_future` → «Расхождение часов сервера, проверь NTP»

Раньше при 401 юзер видел просто «Невалидная подпись Telegram» и не понимал что чинить.

**3. Аватар в кнопке виджета**
Добавлен `data-userpic="true"` — Telegram показывает аватар юзера прямо в кнопке после первого подтверждения (визуально приятнее).

## v0.1.12 — Hotfix: nginx http2 deprecated warning + proxy buffers

**1. `listen ... http2` deprecated warning**

В nginx 1.25+ устарел синтаксис `listen 443 ssl http2;`. Template в репо уже использует новый синтаксис (`listen 443 ssl;` + `http2 on;`), но на проде `nginx/conf.d/app.conf` был отрендерен из старой версии шаблона и не обновлялся при деплоях.

**Фикс:**
- Скрипт `deploy/update-nginx-config.sh` — регенерирует app.conf из template, делает `nginx -t` проверку и graceful reload. Идемпотентный — если конфиг уже актуален, ничего не делает.
- В `deploy/deploy.sh` добавлен автовызов этого скрипта при каждом деплое.

После релиза `app.conf` обновится автоматически и warning исчезнет.

**2. Buffered upstream temp file (производительность)**

В логах: `an upstream response is buffered to a temporary file ... index-daf79621.js` — большие JS-бандлы Vite (>200кб) уходили в temp-file на диск (медленнее).

**Фикс:** в `app.conf.template` подняты proxy-буферы для `location /` (фронт):
```
proxy_buffer_size       16k;
proxy_buffers           8 16k;
proxy_busy_buffers_size 32k;
```
Теперь бандлы держатся в RAM.
