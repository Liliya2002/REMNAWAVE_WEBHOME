# План: страница рассылок Bedolaga + ИИ-автопилот

Отдельная страница «Рассылка сообщений» в разделе Bedolaga Bot: сегменты,
настройки, история с доставляемостью и ИИ, который учится на прошлых рассылках
и — по выбору — либо готовит их, либо отправляет сам.

Реализация — когда решим. Документ фиксирует, что API реально умеет
(проверено запросами на чтение) и какие решения приняты.

**Редакция 2.** Исправлен вывод о влиянии частоты рассылок на блокировки —
см. §2. Автопилот переведён из «нельзя» в переключаемый режим по решению
владельца.

---

## 1. Что выяснилось об API

Всё ниже получено **только GET-запросами** к боевому боту. К `POST /broadcasts`
не обращались: в этом проекте проба этого эндпоинта однажды отправила реальное
сообщение 41 человеку.

### Рассылки уже идут, и активно

За всё время — **110 рассылок**, с января 2026. Это не новая функция, а замена
неудобного интерфейса на удобный.

| Сегмент | Раз использован |
|---|---|
| `all` | 52 |
| `no` | **38** |
| `expired` | 14 |
| `trial` | 3 |
| `expiring` | 3 |

### 🐞 Наш белый список неверен

`services/bedolaga.js` разрешает `['expiring', 'expired', 'active', 'trial', 'all']`.

- **`no` отсутствует** — второй по частоте сегмент (38 из 110). Судя по объёму
  (4 700 против 5 400 у `all`) — пользователи **без подписки**. Через нашу
  админку такую рассылку сейчас **отправить нельзя**.
- **`active` за 110 рассылок не использован ни разу.** Принимает ли его API —
  неизвестно, а проверить можно только ценой реальной отправки тысячам людей.
  В интерфейсе должен стоять с пометкой «не проверен».

Полного списка сегментов взять неоткуда: OpenAPI бот не отдаёт (проверено семь
типовых путей — все 404). Список выше — то, что **фактически применялось**.

### Медиа поддерживается, у нас его нет

В записях есть `has_media`, `media_type`, `media_file_id`, `media_caption`.
Отправлено: **12 с фото, 1 с видео**. Наш `sendBroadcast` умеет только текст.

### Статистика доставки богаче, чем мы показываем

`total_count`, `sent_count`, `failed_count`, `blocked_count`, `status`,
`admin_name`, `completed_at`.

`failed_count` везде 0 — «недоставлено» всегда означает блокировку бота
пользователем, а не сбой. Статус `partial` для рассылок — норма, а не проблема.

### Чего у API нет

- **Отправки конкретным людям или по своему списку.** Только `target_type` из
  фиксированного набора. Ни `user_ids`, ни условий.
- **Отмены и паузы.** Запущенную рассылку не остановить.
- **Планирования на время.** Отправка начинается сразу.
- **`GET /broadcasts/{id}`** — статус ищется перебором списка.

**Следствие для «фильтров кому отправлять»:** произвольных фильтров быть не
может, API их не поддерживает. Реально дать можно удобный выбор из пяти-шести
сегментов **с показом размера аудитории** — сейчас админ выбирает вслепую и не
видит разницы между `all` (5418) и `no` (4744). Подсчёт возможен: `/users`
отдаёт `status`, `has_had_paid_subscription`, `has_made_first_topup`,
`last_activity`, `promo_group`, `subscription`.

## 2. ⚠️ Исправление: частота рассылок блокировки НЕ разгоняет

В первой редакции я написал, что доставляемость падает и «каждая лишняя
рассылка конвертирует часть аудитории в заблокировавших». **Данные этого не
подтверждают.** Вывод был сделан по растущему `blocked_count` без нормировки на
время — то есть неправильно.

Что выяснилось при нормальном разборе 110 рассылок:

**`blocked_count` считается внутри сегмента, а не глобально.** Сравнивать
соседние рассылки разных сегментов нельзя: переход `no` → `trial` даёт «−475
заблокировавших», чего физически не бывает. Сравнивать можно только соседние
рассылки **одного** сегмента.

**Прирост блокировок надо делить на длину интервала.** Сырая дельта растёт
просто потому, что между рассылками прошло больше дней.

По сегменту `all`, 48 корректных интервалов:

| Показатель | Значение |
|---|---|
| Средний интервал между рассылками | 4,6 дн. |
| Новых блокировок в сутки | **13,9** |
| Корреляция «интервал ↔ блокировок в сутки» | **0,04** |
| Частые рассылки (интервал ≤ 2 дн., n=27) | 12,3 блок./сутки |
| Редкие рассылки (интервал ≥ 5 дн., n=13) | **21,0** блок./сутки |

Корреляции нет вовсе. Блокировки идут ровным фоном ~14 человек в сутки
независимо от того, шлёте вы раз в день или раз в три недели. В периоды
затишья их даже больше — люди отваливаются сами, а не от ваших сообщений.

**Что это меняет для плана.** Ограничения частоты в настройках остаются, но как
инструмент владельца, а не как защита от выдуманной угрозы. Жёстко резать
автопилот «чтобы не сжечь базу» оснований нет.

**Чего эти цифры НЕ доказывают.** Наблюдение, не эксперимент: возможно, владелец
сам реже пишет в неудачные периоды, а плохая рассылка всё же вредит — просто
среди 110 их не было заметно. Отсутствие корреляции не то же самое, что
доказанное отсутствие эффекта. Но моё прежнее утверждение данные прямо не
поддерживают, и строить на нём запреты нельзя.

## 3. Страница «Рассылка сообщений»

Роут `/admin/bedolaga/broadcasts`, пункт в `adminNav.js` группы Bedolaga Bot.

### Составление

- **Сегменты карточками**: название, пояснение, **живое число получателей**.
  `active` — отдельно, с пометкой «не проверен на этом боте».
- **Редактор с предпросмотром** ровно как увидит человек в Telegram: HTML
  (`<b>`, `<i>`, `<u>`, `<code>`), ссылки, эмодзи — в существующих рассылках
  разметка используется активно.
- Счётчик длины с порогом Telegram (4096; с медиа — 1024).
- Вложение фото/видео — отдельным этапом, после выяснения, как бот принимает
  файл (`media_file_id` намекает на предзагрузку в Telegram).

### Подтверждение

- Число получателей крупно, сегмент прописью, полный предпросмотр.
- Строка «Отменить или отозвать рассылку нельзя».
- **Ввод числа получателей вручную** для сегментов больше 1000 человек — как
  подтверждение удаления репозитория по имени. Промах мимо кнопки не должен
  стоить 5000 сообщений.

### История

Все 110 рассылок: дата, сегмент, автор, текст, статус, `sent/total`, прирост
блокировок **нормированный на сутки** (§2). График — чтобы тренд был виден в
динамике, а не по одной цифре.

## 4. ИИ: три режима

Режим выбирается на странице настроек одним переключателем.

| Режим | Что делает |
|---|---|
| **Выключен** | Ничего. Рассылки только руками. |
| **Подготовка** | Анализирует, готовит текст и сегмент, кладёт карточку в очередь. Отправляет человек одним кликом. |
| **Автопилот** | Анализирует, готовит и **отправляет сам**, когда сочтёт нужным. |

### Автопилот: окно отмены

Так как у API нет отмены, страховка ставится **до** вызова: приняв решение,
автопилот не отправляет сразу, а ставит рассылку в очередь и шлёт админу в
Telegram уведомление с текстом, сегментом, числом получателей и кнопкой
«Отменить». Через заданное время (по умолчанию 30 минут) уходит отправка.

Это сохраняет автономность — вмешиваться не нужно, всё уйдёт само, — но
оставляет возможность перехватить очевидную ошибку. Окно настраивается,
вплоть до нуля для тех, кому оно не нужно.

### На чём ИИ учится

Главный материал — **110 уже отправленных рассылок**, у каждой есть текст,
сегмент, время и результат доставки. В промпт идут:

- лучшие по результату примеры (низкий прирост блокировок на сутки, высокий
  `sent_count`) — как образцы тона и структуры;
- худшие — как антипримеры;
- отклонённые владельцем предложения с причиной отказа (режим «Подготовка»
  накапливает их сам).

**Метрика качества считается правильно** (§2): прирост блокировок **внутри
того же сегмента**, делённый на число дней с прошлой рассылки. Наивная разность
`blocked_count` дала бы бессмыслицу вида «эта рассылка вернула 475 человек».

Дополнительный контекст: размеры сегментов и их динамика, сколько подписок
истекает на горизонте 3/7/14 дней, когда и по какому сегменту была последняя
рассылка, активные промокоды (`/promo-codes` уже подключены), настройки лимитов.

### Шаблоны

Своя таблица `broadcast_templates` — по образцу `ai_reply_templates` у
ассистента тикетов, с отдельной вкладкой на странице настроек:

| Поле | Смысл |
|---|---|
| `name` | «Новый сервер», «Возврат ушедших», «Напоминание об истечении» |
| `occasion` | когда уместен — текстом, для модели |
| `body` | образец текста с местами для подстановки |
| `target_default` | сегмент по умолчанию |
| `is_active` | участвует ли в подборе |

ИИ выбирает подходящий шаблон под ситуацию и подстраивает текст, а не пишет с
чистого листа. Владелец правит шаблоны — и этим напрямую управляет тем, что
уйдёт людям.

### Схема ответа модели

Тем же механизмом `output_config.format`, что в ассистенте тикетов:

```
should_send      нужна ли рассылка сейчас
target           сегмент
template_id      какой шаблон взят за основу (или null)
message_text     готовый текст
reason           почему именно сейчас и этот сегмент
confidence       0..1
risks            что может пойти не так
```

### Настройки ИИ на странице

- Режим: выключен / подготовка / автопилот.
- Окно отмены для автопилота, минут.
- Частота анализа.
- Какие сегменты ИИ вправе трогать (например, `all` можно оставить только за
  человеком, а `trial` и `expiring` отдать автопилоту).
- Минимальный интервал между рассылками и максимум в неделю.
- Тихие часы — сейчас рассылки уходили и в 03:33.
- Порог уверенности, ниже которого предложение не создаётся.
- Холостой режим — пишет решения в журнал, ничего не создаёт и не шлёт.
  По умолчанию включён, как у ассистента тикетов.

### Жёсткие правила — в коде, не в промпте

По образцу стоп-слов о возвратах: промпт обходится формулировкой, код нет.

- Лимиты частоты, тихие часы и список разрешённых сегментов проверяются **перед**
  вызовом API. Нарушающее решение не отправляется, а пишется в журнал с
  причиной отказа.
- Обещания сроков, сумм возврата и скидок, которых нет среди активных
  промокодов, — проверяются кодом отдельно, а не доверяются модели.
- **Аварийный выключатель**: одна кнопка на странице переводит режим в
  «выключен» и снимает всё из очереди отправки.
- Каждое решение автопилота — в `audit.write()` и в журнал на странице.

## 5. Этапы

1. **Починить белый список и показать аудиторию.** Добавить `no`, пометить
   `active`, считать размер сегмента. Самое ценное и самое дешёвое: закрывает
   невозможность отправить второй по популярности сегмент.
2. **Страница**: составление, подтверждение с вводом числа, история с
   нормированной метрикой блокировок.
3. **Настройки и шаблоны** (миграция `0036`), проверка лимитов перед отправкой.
4. **ИИ в режиме «Подготовка»**: крон, схема ответа, очередь карточек,
   холостой режим, обучение на истории.
5. **Автопилот**: очередь отложенной отправки, окно отмены, уведомление админу,
   аварийный выключатель.
6. **Медиа** — после выяснения, как бот принимает файл.

Каждый этап самостоятелен. Первый можно выкатывать сразу. Порядок 4 → 5 не
случайный: пока ИИ работает в «Подготовке», накапливаются отклонения владельца,
и автопилот стартует уже на них обученным, а не вслепую.

## 6. Проверка

Отправку не проверить «на себе»: минимальный сегмент — десятки людей,
персональной отправки API не поддерживает. Поэтому:

- всё, что не касается отправки (подсчёт сегментов, предпросмотр, история,
  лимиты, метрика блокировок, генерация предложений ИИ), проверяется
  полностью — это GET и своя логика;
- `POST /broadcasts` покрывается тестом с подменённым клиентом: уходит ли
  верный `target`, отбивают ли лимиты запрос, не отправляет ли повтор дважды,
  снимает ли аварийный выключатель очередь;
- расчёт метрики блокировок проверяется на реальных 110 рассылках — в том
  числе на случае со сменой сегмента, где наивная формула даёт отрицательное
  число;
- первая живая отправка — **только на `trial`** (три десятка человек) и руками
  владельца. Первый запуск автопилота — тоже на `trial`.
