# План: система промокодов

Свои промокоды для скидок, бонусных дней и пополнения баланса. Реализация —
когда решим; документ фиксирует решения, чтобы не переизобретать их по ходу.

## 1. Что уже есть, а чего нет

**Чего нет.** Своих промокодов в проекте нет вообще. Таблицы
`bedolaga_promo_uses` и `bedolaga_promo_sync_state` (миграция `0025`) — это
**мониторинг чужого бота продаж**, доступ только на чтение через
`services/bedolaga.js`. Имена `promo_codes` / `promo_code_uses` свободны.

**На что опираемся.** Три механизма уже работают:

| Что нужно промокоду | Готовый механизм |
|---|---|
| Начислить дни подписки | `users.pending_bonus_days` + `POST /api/subscriptions/apply-bonus` |
| Начислить деньги | `user_wallets` + `wallet_transactions` (`addWalletTransaction`) |
| Журнал действий админа | `services/audit.js` → `audit.write()` |

Дни начисляются в `pending_bonus_days`, применяет их пользователь сам — как
реферальные. Своей «промо-валюты» не заводим.

## 2. Что должен уметь промокод

### Типы

| Тип | Значение | Куда идёт |
|---|---|---|
| `percent` | 1–100 | процент скидки на сумму заказа |
| `fixed` | ₽ | фиксированная скидка |
| `days` | дни | `+N` в `pending_bonus_days` |
| `balance` | ₽ | `+N` на кошелёк проводкой `wallet_transactions` |

`percent` и `fixed` привязаны к оплате, `days` и `balance` активируются сами
по себе. В API это разные эндпоинты (§6).

### Ограничения

- `max_uses` — общий лимит (`NULL` = без лимита)
- `max_uses_per_user` — по умолчанию 1
- `starts_at` / `expires_at` — окно действия
- `min_amount` — минимальная сумма заказа для скидки
- `plan_ids[]` — только эти тарифы (пусто = любой)
- `periods[]` — `monthly` / `quarterly` / `yearly` (пусто = любой)
- `first_purchase_only` — только если ещё не было **оплаченной подписки**
  (`payment_type = 'subscription'` со статусом `completed`; пополнение баланса
  покупкой не считается)
- `new_users_only_days` — только зарегистрированным не позже N дней назад
- `assigned_user_id` — **персональный код**: работает только у этого
  пользователя. Нужен для компенсаций за простой — ровно тот случай, когда
  ИИ-ассистент эскалирует тикет человеку, и человеку надо чем-то ответить

## 3. Схема БД

Миграция `0034_promo_codes` — **парная**, `.up.sql` и `.down.sql`, по
конвенции проекта.

```sql
CREATE TABLE promo_codes (
  id                  SERIAL PRIMARY KEY,
  code                VARCHAR(64)  NOT NULL,   -- как ввёл админ, для показа
  code_normalized     VARCHAR(64)  NOT NULL,   -- UPPER, без пробелов и дефисов
  type                VARCHAR(16)  NOT NULL,   -- percent|fixed|days|balance
  value               NUMERIC(12,2) NOT NULL,

  max_uses            INTEGER,
  max_uses_per_user   INTEGER      NOT NULL DEFAULT 1,
  starts_at           TIMESTAMPTZ,
  expires_at          TIMESTAMPTZ,
  min_amount          NUMERIC(12,2),
  plan_ids            INTEGER[]    NOT NULL DEFAULT '{}',
  periods             TEXT[]       NOT NULL DEFAULT '{}',
  first_purchase_only BOOLEAN      NOT NULL DEFAULT false,
  new_users_only_days INTEGER,
  assigned_user_id    INTEGER REFERENCES users(id) ON DELETE CASCADE,

  is_active           BOOLEAN      NOT NULL DEFAULT true,
  batch_label         VARCHAR(64),
  comment             TEXT,
  created_by          INTEGER REFERENCES users(id) ON DELETE SET NULL,
  created_at          TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
  updated_at          TIMESTAMPTZ  NOT NULL DEFAULT NOW()
);

CREATE UNIQUE INDEX promo_codes_normalized_uniq ON promo_codes (code_normalized);

CREATE TABLE promo_code_uses (
  id               SERIAL PRIMARY KEY,
  -- RESTRICT, не CASCADE: журнал активаций обязан пережить код. Удаление
  -- кода с активациями должно падать на уровне БД, а не тихо стирать историю.
  promo_id         INTEGER NOT NULL REFERENCES promo_codes(id) ON DELETE RESTRICT,
  user_id          INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  payment_id       INTEGER REFERENCES payments(id) ON DELETE SET NULL,

  status           VARCHAR(16) NOT NULL,       -- reserved|applied|released
  discount_amount  NUMERIC(12,2),
  granted_days     NUMERIC(10,2),
  granted_balance  NUMERIC(12,2),
  original_amount  NUMERIC(12,2),              -- цена до скидки, для отчётов
  over_limit       BOOLEAN NOT NULL DEFAULT false,  -- подтверждено сверх лимита

  reserved_until   TIMESTAMPTZ,
  created_at       TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  applied_at       TIMESTAMPTZ,
  released_at      TIMESTAMPTZ
);

-- Повторный webhook не должен задвоить активацию
CREATE UNIQUE INDEX promo_uses_payment_uniq
  ON promo_code_uses (promo_id, payment_id) WHERE payment_id IS NOT NULL;

CREATE INDEX promo_uses_user_idx   ON promo_code_uses (promo_id, user_id);
CREATE INDEX promo_uses_status_idx ON promo_code_uses (status, reserved_until);
```

Счётчик использований отдельным полем **не храним** — считаем по
`promo_code_uses`. Денормализованный счётчик пришлось бы держать в согласии с
журналом при каждом откате, и он бы разъехался.

## 4. Резерв, а не мгновенное списание

Оплата через шлюз живёт до 30 минут и может не состояться. Когда считать код
использованным?

- **При создании платежа** — брошенная оплата сжигает активацию.
- **При подтверждении** — пользователь откроет пять вкладок с одноразовым
  кодом и оплатит все пять.

Поэтому три состояния:

```
reserved  ──payment completed──→  applied
    │
    └──payment failed/expired──→  released
```

### Правило 1: корректность не зависит от крона

В лимитах учитываются `reserved` и `applied`, но `reserved` с истёкшим
`reserved_until` **не учитывается запросом лимита**. То есть код освобождается
сам, по времени. Крон нужен только чтобы проставить `released` для отчётов —
если он не отработает, ничего не сломается. Вешаем на существующий
`expireOldPayments` (`services/payment.js`), отдельной задачи не нужно.

### Правило 2: `reserved_until` = час, а не `payments.expires_at`

Соблазнительно взять `payments.expires_at`, но на момент резерва его **ещё
нет**: в `POST /create` он записывается только после ответа Platega
(`routes/payments.js`, `UPDATE ... SET expires_at` идёт после
`createPayment()`). Ставим `NOW() + 1 hour` — тот же запас, что использует
`expireOldPayments` для платежей без `expires_at`. Одно правило, никакой
зависимости от порядка вызовов.

### Правило 3: на подтверждении лимит не проверяется

Самое важное. Мы только что выпустили `v0.2.1`, где починили ровно это:
платёж в статусе `expired` **может** стать `completed` — подтверждение по СБП
приходит и через час. Значит резерв мог истечь и уйти другому, а потом придёт
подтверждение оплаты.

Отказать в скидке человеку, который уже заплатил, — хуже, чем выпустить
101 активацию вместо 100. Поэтому `confirm()` применяет скидку **всегда**,
ставит `over_limit = true` и пишет предупреждение в лог плюс уведомление
админу. Лимит — инструмент планирования, а не защита от денег.

### Правило 4: ошибка шлюза освобождает резерв

`createPayment()` умеет бросать (403 от Platega мы уже ловили). Платёж и
резерв к этому моменту уже вставлены, поэтому в `catch` резерв освобождается
явно. Даже если освобождение не сработает, правило 1 закроет вопрос через час.

## 5. Куда встраивается

| Поток | Файл | Промокод |
|---|---|---|
| Покупка подписки через шлюз | `routes/payments.js` → `POST /create` | уменьшает `amount` |
| Покупка подписки с баланса | `routes/payments.js` → `POST /pay-with-balance` | уменьшает списание |
| Смена тарифа | `routes/subscriptions.js` → `createChangeGatewayPayment` / `payChangeFromBalance` | уменьшает доплату |
| Докупка трафика сквада | `routes/subscriptions.js` (`squad_traffic_topup`) | **не применяем** в первой версии |
| Пополнение баланса | `routes/payments.js` → `POST /topup/create` | **не применяем** |
| Активация без покупки | новый `POST /api/promo/redeem` | `days` / `balance` |

**Почему пополнение исключено.** Скидка на пополнение — продажа рублей дешевле
рубля: положил 900, получил 1000 на баланс, потратил на что угодно, включая
обход ограничений других промокодов (`plan_ids`, `first_purchase_only`). Если
механика понадобится — отдельный тип «бонус к пополнению» со своими лимитами.

**Почему докупка трафика исключена** пока: суммы там мелкие, а поток отдельный
(`subscriptions.js:819/858`). Добавить потом — одна строка вызова `validate`.

Расчёт живёт в одном месте — `services/promoCodes.js`:

```
validate(code, { userId, planId, period, amount })
  → { ok, promo, discount, finalAmount } | { ok: false, reason }
reserve(client, promo, { userId, paymentId, discount, originalAmount })
confirm(client, paymentId)    // лимит НЕ проверяет
release(client, paymentId)
redeem(userId, code)          // days | balance
```

Клиент передаёт **только строку кода**. Сумма, скидка и итог никогда не
приходят с фронта.

### Округление

Скидка считается один раз, на сервере, и **сохраняется**. На подтверждении
берётся сохранённое значение, а не пересчитывается — иначе смена настроек
кода между оплатой и вебхуком изменила бы сумму.

Правило: `discount = round(amount * percent / 100, 2)` с округлением **вверх**
(в пользу клиента), `finalAmount = amount - discount`, не меньше нуля. Оба
значения пишутся с точностью 2 знака: `payments.amount` — `NUMERIC(12,2)`, и
именно с ним вебхук сверяет пришедшую сумму.

### Порог шлюза

Скидка может дать сумму вроде 1 ₽, которую СБП не проведёт. Нужны две ветки:

- `finalAmount == 0` — активируем подписку **сразу, в транзакции, без
  обращения к Platega**. Образец — `POST /api/payments/pay-with-balance`.
- `0 < finalAmount < порог шлюза` — предлагаем оплату с баланса вместо
  шлюза. **Минимальную сумму Platega надо уточнить** перед реализацией
  четвёртого этапа; в документации, которую я смотрел, её нет.

## 6. API

**Пользовательские** (`routes/promo.js`, всё под `verifyToken`):

- `POST /api/promo/preview` — `{ code, plan_id, period }` → сумма до, скидка,
  итог либо причина отказа. Ничего не резервирует. POST, а не GET, потому что
  проверка кода — это тело запроса и её не надо кешировать; правило «ретраи
  только для GET» тут не при чём, эндпоинт ничего не меняет.
- `POST /api/promo/redeem` — `{ code }` для `days` / `balance`.

Существующие эндпоинты получают необязательное `promo_code`:
`POST /api/payments/create`, `POST /api/payments/pay-with-balance`,
`POST /api/subscriptions/change`.

### Защита от перебора

`preview` позволяет перечислять коды. Глобальный лимитер — 1000 запросов за
15 минут (`index.js:68`), этого хватит, чтобы прогнать словарь вида `SALE20`,
`NEWYEAR`, `PROMO10`. Нужен свой лимитер на `/api/promo`, считающий **неудачные
попытки**: порядка 20 за 15 минут на пользователя, успешные не штрафуются.
Плюс генератор кодов по умолчанию делает их случайными (§7) — угадать
осмысленное слово легко, случайные восемь символов нет.

**Админские** (`routes/admin-promo.js`, по образцу `admin-selectel.js`):

- `GET /api/admin/promo` — список с фильтрами и счётчиками
- `POST /api/admin/promo` — создать
- `PUT /api/admin/promo/:id` — изменить
- `POST /api/admin/promo/:id/deactivate` — выключить; удаления нет (см. §3)
- `POST /api/admin/promo/bulk` — сгенерировать пачку
- `GET /api/admin/promo/:id/uses` — кто и когда активировал
- `GET /api/admin/promo/export` — CSV

Все изменения — через `audit.write()`.

## 9. Влияние на реферальную программу

Проверено по коду: вознаграждение считается от `payments.amount`
(`services/payment.js:266` → `referralService.processPaymentReward`). Так как
в `payments.amount` лежит сумма **со скидкой**, пригласивший получает процент
от неё. Это осознанное решение: платим процент с того, что реально получили.

Побочный эффект, о котором надо знать: в `referral_config` есть
`min_payment_for_reward`. Скидка может увести платёж **под этот порог**, и
пригласивший не получит ничего — молча. Варианты: либо принять это, либо
считать вознаграждение от `original_amount`. Рекомендую принять и написать в
описании реферальной программы, что процент считается с фактически оплаченной
суммы.

Промокод и реферальный бонус **складываются** — это разные механики, обе дают
дни через `pending_bonus_days`. А **два промокода на один платёж — нет**:
`promo_code` в запросе один. Иначе `min_amount` и проценты превращаются в
задачу о порядке применения.

## 10. Грабли

**Сумма в `payments.amount` обязана быть итоговой, со скидкой.** Вебхук
сверяет пришедшую сумму с `payments.amount` (`processPlategaWebhook`). Запишем
полную цену, а спишем со скидкой — увидим недоплату и отобьём подтверждённый
платёж. Оригинал храним в `promo_code_uses.original_amount`, не в `payments`.

**Гонка на лимите.** Два параллельных запроса с последней активацией пройдут
оба, если считать `SELECT count(*)` без блокировки. Резерв — под
`SELECT ... FROM promo_codes WHERE id = $1 FOR UPDATE` в той же транзакции,
что и вставка в `promo_code_uses`.

**Повторный вебхук.** Уникальный индекс `(promo_id, payment_id)` — та же
защита, что у ИИ-ассистента на `(account_id, ticket_id, last_message_id)`.

**Регистр и похожие символы.** Ищем по `code_normalized`, показываем как ввёл
админ. Кириллицу в кодах не допускаем вовсе: «СКИДКА» латиницей и кириллицей
выглядят одинаково, а это разные строки — ту же ловушку разбирали в
детекторе возвратов у ИИ-ассистента.

**Чарджбэк по оплате со скидкой.** Переход `completed → refunded` переводит
активацию в `released`, иначе код останется потраченным на отменённую покупку.

**Мультиаккаунт обходит `max_uses_per_user`.** Известная грабля проекта: один
человек легко получает два аккаунта — вход через бота ищет по `telegram_id`,
через браузер по `telegram_oidc_sub`. Лимит «одна активация на пользователя»
обходится вторым аккаунтом, и полностью это не лечится. Что можно: считать
активации ещё и по `users.registration_ip` и по `telegram_id`, показывать
админу подозрительные совпадения в журнале. Жёстко блокировать по IP нельзя —
за одним адресом сидит целый дом.

**Пул PostgreSQL и вложенные транзакции.** `reserve` / `confirm` / `release`
работают на **переданном** клиенте (`client`), а не на `db.query` — иначе
уйдут мимо транзакции вебхука, и откат оставит несогласованное состояние.

## 11. Этапы и проверка

Каждый этап выкатывается отдельно.

1. **Схема и сервис.** Миграция `0034` (`.up` + `.down`),
   `services/promoCodes.js`. Проверка расчёта и ограничений без HTTP.
2. **Админка.** `routes/admin-promo.js`, страница, генератор пачки, журнал.
   Коды уже можно заводить, но они нигде не применяются — выкатывать
   безопасно. Здесь же переименование Bedolaga-пункта.
3. **Активация без покупки.** `redeem`, типы `days` / `balance`, кнопка в
   кабинете, лимитер на `/api/promo`. Платежей не касается.
4. **Скидки в оплате.** Разбит надвое, потому что скидка на доплату при
   смене тарифа считается от результата пропорционального пересчёта
   (`calculateChange`) и заслуживает отдельного разбора, а не торопливого
   довеска к покупке.
   - **4a — покупка подписки. СДЕЛАНО.** `preview`, `promo_code` в
     `POST /payments/create` и `POST /payments/pay-with-balance`, резерв /
     подтверждение / освобождение в вебхуке, уборка резервов в
     `expireOldPayments`, ветки нулевой суммы и порога шлюза, поле промокода
     в форме оплаты.
   - **4b — смена тарифа. СДЕЛАНО.** `promo_code` в
     `POST /subscriptions/change`; скидка считается от ДОПЛАТЫ
     (`calc.payDifference`), ограничения кода по тарифу — против целевого.
     `preview` получил второй режим для смены тарифа: базу считает сервер
     через `calculateChange`, клиент сумму не присылает.
     Проверка кода и резерв перенесены ВНУТРЬ транзакций
     `payChangeFromBalance` / `createChangeGatewayPayment` под `FOR UPDATE` —
     в роуте осталась только предварительная проверка для выбора ветки.
     Попутно исправлен боевой баг: оба этих потока звали
     `platega.createTransaction`, которой в модуле не существовало, поэтому
     оплата смены тарифа и докупки трафика картой падала с TypeError.
   Минимальная сумма шлюза вынесена в константу `MIN_GATEWAY_AMOUNT`
   (`routes/payments.js`), значение 10 ₽ взято по аналогии с минимумом
   пополнения — **уточнить у Platega и проверить на проде**.
5. **Бот и отчёты. СДЕЛАНО.** Команда `/promo <код>` со своим лимитером
   попыток (HTTP-лимитер на бота не распространяется — он ходит в сервис
   мимо Express); уведомление `user_promo_applied` — только из веб-роута,
   потому что бот отвечает пользователю сам; `GET /api/admin/stats/promo`
   и сводка на странице промокодов. CSV сделан ещё на втором этапе.

Обязательный прогон перед четвёртым этапом — на живой схеме, как проверяли
исправление зачисления в `v0.2.2`:

- `percent` и `fixed`: итог совпадает с тем, что ушло в шлюз, и с
  `payments.amount`;
- скидка 100 %: подписка активирована, обращения к Platega не было;
- одноразовый код в двух параллельных запросах: вторая попытка отклонена;
- брошенная оплата: через час код снова доступен **без участия крона**;
- **платёж подтверждён после истечения резерва**: скидка применена,
  `over_limit = true`, админ уведомлён;
- повторный вебхук по тому же платежу: активация не задвоилась;
- чарджбэк: активация освобождена;
- ошибка шлюза при создании: резерв освобождён;
- код чужого тарифа, просроченный, исчерпанный, персональный на чужом
  аккаунте, для новых пользователей на старом аккаунте — отклонены с внятной
  причиной;
- 25 неверных кодов подряд: сработал лимитер.

Telegram-часть проверяется только на проде — нужен публичный HTTPS.

## 12. Что исправлено после перепроверки

Разбор первой редакции этого документа.

**Логическая дыра.** Резерв мог истечь, а платёж — всё равно подтвердиться:
именно это поведение мы починили в `v0.2.1`, где `expired` перестал быть
тупиком. Первая редакция проверяла бы лимит на подтверждении и отказала бы в
скидке человеку, который уже заплатил. Добавлено правило 3 в §4 и флаг
`over_limit`.

**Самопротиворечие.** В тексте было «код не удалять, журнал должен пережить»,
а в схеме стоял `ON DELETE CASCADE` на `promo_id` — то есть удаление кода
стирало бы журнал. Заменено на `RESTRICT`.

**Невыполнимое `reserved_until`.** Было `= payments.expires_at`, но на момент
резерва его ещё нет: он записывается после ответа Platega. Заменено на
фиксированный час.

**Пропущено:**

- правило округления скидки — процент от 599 ₽ даёт копейки, и без явного
  правила `payments.amount` и сумма в шлюзе могли разойтись;
- минимальная сумма шлюза: скидка может дать 1 ₽, который СБП не проведёт;
- защита от перебора кодов — глобальных 1000 запросов за 15 минут хватает на
  словарь;
- влияние на рефералов: вознаграждение считается от суммы со скидкой, и
  `min_payment_for_reward` может молча обнулить выплату;
- шестой поток оплаты — докупка трафика сквада;
- освобождение резерва при ошибке шлюза;
- персональные коды (`assigned_user_id`) для компенсаций;
- обход `max_uses_per_user` через второй аккаунт в Telegram;
- парный `.down.sql`;
- четыре параллельных списка в `AdminTelegram.jsx` при добавлении уведомления;
- коллизия в меню админки с существующим пунктом «Промокоды» у Bedolaga;
- уточнение `first_purchase_only`: считается только оплаченная подписка,
  пополнение баланса покупкой не считается.

**Переформулировано.** Обоснование `preview` как POST было перевёрнутым:
ссылался на правило «ретраи только для GET», хотя правило существует ровно
потому, что POST меняет состояние, а `preview` не меняет ничего.
