# ИИ-агент эксплуатации: план

Автономный агент, который следит за инфраструктурой, сам разбирается в сбоях
и сам их чинит. Составлено 11.08.2026, реализация — по решению владельца.

Это продолжение линии, начатой ассистентом поддержки (`services/aiAssistant.js`):
там уже отработан рабочий шаблон — холостой режим, эскалация при любой
неопределённости, журнал всего, что сделано и не сделано. Здесь то же самое,
но ставки выше: ошибка в тикете стоит неловкого сообщения, ошибка в проде —
лежащего сервиса.

---

## Главное решение: каталог действий вместо шелла

Соблазн — дать агенту SSH и сказать «чини». Так делать нельзя, и не из
осторожности, а потому что это не работает: обвязка видит только строку команды
и не может ни ограничить её, ни осмыслить, ни откатить.

Вместо этого агент получает **набор типизированных инструментов**: `restart_xray`,
`reboot_vps`, `free_disk_space`, `reactivate_subscription`. У каждого — известный
эффект, известная обратимость, свой лимит частоты и своя политика.

Что это даёт:

- обвязка может **отказать** в конкретном действии, не отказывая во всех
- каждое действие логируется с параметрами, а не как `bash -c "..."`
- на действие вешается ограничитель частоты и проверка предусловий
- безопасные действия идут параллельно, опасные — строго по одному

95% реальных сбоев в этом проекте лечатся десятком типовых действий. Каталог
из десяти инструментов покрывает почти всё, оставаясь при этом управляемым.

---

## Четыре уровня действий

Организующий принцип — **обратимость**, а не важность.

| Уровень | Что это | Примеры | Режим |
|---|---|---|---|
| **0. Чтение** | Ничего не меняет | логи, метрики, `df`, статус нод, API-запросы | Всегда, без спроса |
| **1. Самолечение** | Обратимо, эффект локальный | перезапуск xray, ротация логов, чистка кэша, повторная активация подписки | Автоматически, с лимитом частоты |
| **2. Заметное** | Восстановимо, но клиенты заметят | ребут VPS, вывод ноды из ротации, перенос юзеров между сквадами | Автоматически при подтверждении из ≥2 источников и в рамках бюджета |
| **3. Необратимое** | Деньги, данные, внешний мир | создание/удаление серверов, рассылки, возвраты, смена DNS, правка платёжных ключей | **Никогда сам.** Готовит заявку — жмёте вы |

Третий уровень остаётся человеческим навсегда. Не на первое время — навсегда.
Ровно там живут действия, которые нельзя отменить: удалённый сервер не вернуть,
отправленную рассылку не отозвать. У нас уже был случай, когда при пробе API
ушла реальная рассылка на 41 человека — это ровно та категория.

## Пять ограничителей

Без них любой автономный агент рано или поздно устраивает аварию. Каждый решает
конкретный сценарий отказа.

### 1. Подтверждение из нескольких источников

Никогда не действовать по одному сигналу. Мы это уже проходили: `check-host.net`
показывает ноду недоступной, когда проблема у самого check-host.

Прежде чем считать ноду упавшей, нужно ≥2 независимых подтверждения из:
внешняя проверка, статус в RemnaWave, SSH-проба, отсутствие трафика.

### 2. Ограничение радиуса

Жёсткие потолки, зашитые в код:

- не больше N действий уровня 2 в час
- одновременно чинится **одна** нода, не весь флот
- не трогать больше X% инфраструктуры за окно
- превышение любого потолка — стоп и эскалация

Это защита от каскада: DNS моргнул, агент решил, что упало всё, и пошёл
перезагружать двадцать серверов подряд.

### 3. Размыкатель цикла

Одно и то же действие на одну цель N раз за M минут — цель **карантинится**:
автоматика по ней отключается, зовётся человек.

Перезапуск, который не помогает, но выполняется в сотый раз, — это не лечение,
это маскировка проблемы и лишний простой.

### 4. Обнаружение собственной слепоты

**Отсутствие сигнала — не отрицательный сигнал.** Если упал сам источник
мониторинга (check-host недоступен, API RemnaWave не отвечает, у агента нет
сети), агент обязан понять, что ослеп, и **ничего не делать**, а не решить,
что лежит вся инфраструктура.

Реализация: каждый источник имеет отдельную проверку живости, и при её отказе
все выводы, опирающиеся на этот источник, помечаются недостоверными.

### 5. Рубильник

Один флаг останавливает всю автономность мгновенно. Плюс отдельные флаги на
каждый уровень и на каждый инструмент. Доступен из админки без деплоя.

## Что мониторим

Часть уже работает кронами — агент их не заменяет, а надстраивается: получает
их выводы как сигналы.

| Область | Источник | Уже есть |
|---|---|---|
| Доступность VPS | check-host.net, TCP/443 | `cron/vpsHealth.js` |
| Статус нод и xray | RemnaWave API | частично |
| Место на диске нод | SSH `df` | нет |
| Срок сертификатов | проверка TLS | нет |
| Оплата → активация | сверка `payments` ↔ `subscriptions` | нет |
| Здоровье Platega | пинг API | нет |
| Живость Telegram-бота | heartbeat | нет |
| Пул PostgreSQL | метрики `pg` | нет |
| Аномалии трафика | свои детекторы | `trafficGuard`, `p2pDetector` |
| Живость самих кронов | heartbeat каждого | нет |
| Баланс провайдеров | API провайдеров | `selectelBalance` |
| Доступность Bedolaga | пинг API | нет |

**Живость кронов — недооценённый пункт.** Молча умерший крон опаснее упавшей
ноды: ничего не сломано, просто перестало проверяться. Каждый крон должен
отмечаться в таблице, а агент — замечать пропущенные отметки.

---

## Плейбуки: симптом → действие

Ядро системы. Не промпт, а таблица в БД, редактируемая человеком: агент выбирает
из неё, а не изобретает лечение на ходу.

| Симптом | Как проверить | Действие | Уровень |
|---|---|---|---|
| Нода не отвечает TCP/443 | check-host + RemnaWave + SSH | перезапуск xray | 1 |
| xray жив, трафика нет | логи xray, `systemctl status` | перезапуск ноды | 2 |
| Диск >90% | `df` по SSH | ротация логов, чистка `/tmp` | 1 |
| Сертификат истекает <7 дней | проверка TLS | `certbot renew` | 1 |
| Оплачено, но не активировано | сверка таблиц | повторная активация | 1 |
| Нода упала третий раз за час | история инцидентов | вывести из ротации, позвать человека | 2 |
| Platega не отвечает >10 мин | пинг API | уведомить, показать баннер | 3 |
| Баланс провайдера < 7 дней | API провайдера | уведомить | 3 |
| Бот не отвечает | heartbeat | перезапуск процесса | 1 |
| Крон молчит >2 интервалов | таблица отметок | перезапуск воркера | 1 |

Плейбуки правятся в админке. Агент может **предложить** новый по итогам
разобранного инцидента, но добавляется он только с вашего согласия.

## Схема данных

```
ai_ops_incidents     обнаруженная проблема: симптом, доказательства,
                     статус, что предпринято, чем кончилось
ai_ops_actions       каждое действие: инструмент, цель, параметры, уровень,
                     кто разрешил, результат, откат
ai_ops_playbooks     симптом → действие, редактируется человеком
ai_ops_policy        по каждому инструменту: включён, уровень, лимит частоты,
                     авто или заявка
ai_ops_heartbeats    отметки живости кронов и внешних источников
ai_ops_settings      ключ провайдера, модель, рубильник, бюджеты
```

`ai_ops_actions` — источник правды для разбора полётов. Пишется **до** попытки,
а не после: действие, оборвавшееся на середине, должно оставить след.

## Этапы внедрения

Прыгнуть сразу в полную автономию нельзя — не из осторожности, а потому что
не на чем основывать решение. Каждый этап даёт данные для следующего.

**Этап 0 — наблюдение.** Агент только смотрит и заводит инциденты. Ничего не
делает и не предлагает. Цель: понять, что вообще ломается и как часто. Пара
недель. Здесь же вылезут ложные срабатывания — их дешевле ловить сейчас.

**Этап 1 — предложения.** Агент предлагает действие, вы жмёте кнопку. Метрика
одна: **как часто он прав**. Если ниже 90% на уровне 1 — дальше идти рано.

**Этап 2 — автоматический уровень 1.** Перезапуски и чистки идут сами.
Остальное — заявками. Здесь автономность уже ощущается: рутина уходит.

**Этап 3 — автоматический уровень 2.** Ребуты и вывод нод, при подтверждении
и в рамках бюджета.

**Уровень 3 не автоматизируется никогда.**

Между этапами — не «прошло время», а выполненный критерий. Точность на живых
инцидентах, ноль неоправданных действий, работающий размыкатель цикла.

## Риски

**Агент ломает, пока чинит.** Основной. Лечится уровнями, обратимостью,
холостым режимом и обязательным откатом у каждого инструмента уровня 2.

**Маскировка проблемы.** Перезапуск раз в 10 минут выглядит как «работает»,
а на деле — деградация. Лечится размыкателем цикла и тем, что повторный
инцидент по той же цели повышается в приоритете, а не гасится.

**Инъекция через пользовательские данные.** Недооценённый вектор и главная
причина не давать агенту шелл. Логи, тикеты, имена пользователей, User-Agent —
всё это текст, который пишет посторонний человек. Клиент может отправить
сообщение, составленное как инструкция агенту.

Защита двухслойная: наблюдаемые данные попадают в контекст **только как данные**,
никогда как инструкции; и каталог инструментов остаётся жёсткой границей —
даже успешная инъекция не даст выполнить действие, которого нет в каталоге.

**Стоимость.** Агент, зациклившийся на сломанной системе, жжёт токены быстро.
Нужен потолок трат за сутки, при достижении — переход в режим наблюдения.

**Сторонний провайдер модели.** Сейчас ассистент поддержки ходит через Customix.
Для эксплуатации это чувствительнее: в контекст агента попадут адреса серверов,
топология, куски логов, иногда — секреты, случайно попавшие в вывод.

Рекомендация: для агента эксплуатации подключаться к Anthropic напрямую, а не
через перепродавца. Разница в цене несопоставима с ценой утечки инфраструктурных
данных.

## Что понадобится, чего сейчас нет

- **Heartbeat-таблица и отметки во всех кронах** — иначе молча умерший крон
  не заметить. Полезно само по себе, независимо от агента.
- **`ENCRYPTION_KEY` на проде** — сейчас не выставлен, секреты лягут в базу
  открытым текстом. Для агента эксплуатации это критичнее, чем для тикетов.
- **Инвентарь SSH-доступов** с учётом грабли про заблокированный исходящий
  порт 22 и `ssh.socket` в Ubuntu 22.10+.
- **Откат у каждого инструмента уровня 2** — действие без описанного отката
  автоматизировать нельзя.
- **Тестовый стенд.** Обкатывать плейбуки на проде — плохая идея; нужна хотя бы
  одна нода, которую не жалко.

## Чем это отличается от «просто написать кроны»

Резонный вопрос: половина плейбуков — это `if диск полный → почисти`, для чего
модель не нужна.

Верно, и такие вещи надо делать кронами: дешевле и надёжнее. Модель нужна там,
где детерминированное правило не составить:

- **связывание сигналов** — упали три ноды у одного провайдера и просела оплата:
  это три инцидента или один?
- **разбор незнакомого** — сбой, на который плейбука нет: собрать факты,
  сформулировать гипотезу, предложить проверку
- **чтение логов** — вытащить причину из простыни вывода
- **приоритизация** — что чинить первым, когда сломалось несколько
- **объяснение** — внятный рассказ, что произошло, вместо стены метрик

То есть модель — это диспетчер и диагност, а исполнители — обычный детерминированный
код. Плейбуки пишутся кронами, агент решает, когда и какой запустить, и разбирается
с тем, чего в плейбуках нет.

Такое разделение и надёжнее, и дешевле: модель зовут раз в несколько минут на
короткий разбор, а не гоняют в цикле.
